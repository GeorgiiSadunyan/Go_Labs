# Документация: Тесты WebRTC сервера (internal/webrtc/server_test.go)

Этот файл содержит **интеграционные тесты API**. Мы не тестируем здесь реальное видео (это невозможно без браузера), но мы тестируем весь механизм "рукопожатия" (handshake), который происходит *до* начала звонка.

Для тестов используется пакет `httptest`, который позволяет "притвориться" браузером и отправлять запросы в функции-хендлеры напрямую.

## 1. TestHandleLogin (Авторизация)
**Что тестирует:** Ручку (endpoint) `/api/auth/login`.
**Зачем:** Убедиться, что сервер выдает JWT-токен в обмен на имя пользователя.

* **Как работает:**
    1.  Создается фейковый POST-запрос с JSON-телом `{"username": "testuser"}`.
    2.  Используется `httptest.NewRecorder()` — это "виртуальный диктофон", который записывает ответ сервера вместо того, чтобы отправлять его по сети.
    3.  Вызывается функция `handleLogin`.
    4.  **Проверка:**
        * Статус ответа должен быть `200 OK`.
        * В ответе (JSON) должно быть поле `token`, и оно не должно быть пустым.

## 2. TestCreateSession (Создание звонка)
**Что тестирует:** Ручку `/api/session` и защиту Middleware.
**Зачем:** Это сложный тест. Он проверяет, что нельзя создать звонок без авторизации, и что сессия создается с правильными параметрами.

* **Сценарий теста:**
    1.  **Подготовка:** Сначала мы "вручную" генерируем валидный токен для пользователя `callerUser` (используя внутреннюю функцию `generateToken`).
    2.  **Запрос:** Формируем POST-запрос с JSON `{"targetUsername": "friendUser"}`.
    3.  **Авторизация:** Самое важное — мы добавляем заголовок `Authorization: Bearer <ТОКЕН>`. Без этого сервер должен отвергнуть запрос.
    4.  **Выполнение:** Мы оборачиваем хендлер в `authMiddleware`, чтобы протестировать и проверку токена тоже.
    5.  **Проверка:**
        * Статус `200 OK`.
        * В ответе JSON поле `caller` равно `callerUser`.
        * В ответе поле `status` равно `pending` (ожидание).
